# Native Project / Environment / Deployment binding

`include/ud/project.h` adds an immutable Project loader and binder, not an execution API. A Project version-3 document contains `id`, typed `parameters`/`variables`, shared `connections`, and exact Package references `packages: [{id, revision}]`. Packages retain their existing definition; references do not embed another control-flow language.

An Environment has `version`, `id`, `projectId`, `projectParameters` and per-Package `packageParameters`. Binding checks the project identity, reference revision, unknown parameter names and scalar types. The precedence of parameter values is explicit execution override, then Environment value, then definition default. Required values must exist at binding. Current scalar parameters/variables are bool/int64/float64/utf8, with the existing native value parser and NULL semantics; broader typed expressions remain G02/G04/G05 work.

`ud_project_bind` returns a native Package plus owned Package parameter JSON. The Package includes an immutable `project` scope; no runtime dependency on the input Project/Environment objects remains. Existing `ud_execution_create` owns its copies and one resource context. Native resolution searches Task → Container → Package → Project, selecting mutable variables and then read-only parameters at each scope. Writes cannot bypass a nearer read-only parameter to mutate an outer variable. Set/For/Foreach assignment validation rejects read-only targets before running.

Logical connections use one Connection Manager lookup, including Data Flow prevalidation. Package connection definitions shadow Project definitions with the same id. A Project shared connection's parameter/variable expressions resolve in its owning Project scope, so a Package's same-named parameter cannot silently change its resource. Connections still use existing authorization, physical driver and host credential resolver contracts.

Catalog Project and Environment documents now have domain validation. A Deployment has `version`, `id`, an exact Project `{id,revision}` and optional Environment `{id,revision}`. Publishing it validates referenced Package existence and Environment names/types. It does not open drivers or run components. `ud_catalog_bind_package` rechecks authorization and resolves the exact immutable references, calls the native Project binder, and preserves the selected Deployment/Project/Environment/Package revisions in the Package's `deployment` metadata. This metadata contributes to the existing Package fingerprint, making checkpoint identity sensitive to deployment revision changes.

Version selection and rollback are explicit selections of immutable Deployment revisions. There is no mutable implicit “latest” alias or background executor. Activation routing, retention/deletion, distributed repositories, a complete Audit model and full execution-history/trace/lineage integration remain outstanding G47/G48 work. Their absence does not invalidate the implemented immutable version selector, but those broader goals remain open.

`tests/project.c`/`.py` cover four scope levels, parameter shadowing/immutability, Project-owned shared connections, overrides/type/name/revision errors, Catalog restart, Deployment version switching and rollback. Every successful execution is repeated through the existing checkpoint resume API; Project variables and output counts are restored without duplicate output. `package_language_parity.py` now also exercises Project parameters/shared connections and scope shadowing through unchanged C/.NET/Java execution projections. Saved results and source hashes are under `docs/acceptance/evidence/ssis-project`.
