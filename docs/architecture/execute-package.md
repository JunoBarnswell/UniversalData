# Execute Package Task on one Execution core

`executePackage` is a real nested Package definition frame. Its configuration is `{package: <version-3 Package>, parameters: {childName: <native expression AST>}}`. Parent expression values are mapped explicitly into read-only child parameters. The old draft container form using `children` is rejected. External Package/version selection belongs to the existing Catalog/host loader; the task runs the resulting canonical Package definition.

`engines/package/child.c` owns frame setup/teardown. It parses with `ud_package_create`, uses the shared root binder and validator, and calls the same control-flow execution service as the root Package. The existing Execution handle, quota context, component registry, authorization/resolver callbacks, cancellation token, deadline, metrics and checkpoint Journal are preserved. It creates no other execution core, scheduler, thread, resource quota or recovery store.

Each child has independent Package/Project variable roots, parameter definitions and logical connections. The parent lexical roots are restored before the enclosing task completes. Parent variables are visible only while evaluating explicit input mappings; they are not implicitly available inside the child. Child configuration references bind in child scopes. Child/grandchild errors, cancellation and CommitUnknown propagate to the parent. Failure handlers use the same control-flow service and preserve the original error; cancelled/unknown outcomes do not run them.

Child lifecycle events identify the child Package, the root execution id and a qualified task path containing the child Package id. Task/checkpoint paths include length-prefixed identifiers, so two calls or loop iterations do not collide. The enclosing definition fingerprint covers the embedded child definition; child tasks and file/SQL effects use the existing recovery contract. A completed parent invocation resumes from its parent-scope snapshot, not by injecting child variables into the caller.

Nested depth is bounded by the existing depth policy and JSON quota. Output-variable mapping, lazy remote loading and child-specific parallel scheduling are not part of this contract. Hosts that need another published version can bind it through Catalog before constructing the task. This does not create another execution DSL.

`tests/child_package.c` verifies that native callbacks receive the identical Execution/context, that child parameter/variable names are isolated, and that parent roots survive child/grandchild success or failure. Its Python driver checks mapping/type/name failures, cancellation, CommitUnknown, nesting/depth, legacy-alias rejection and real process termination after a child checkpoint followed by two resumes. The three-language parity Package now executes its 10,003-row pipeline inside a real child with mapped output parameters. Evidence is under `docs/acceptance/evidence/ssis-child-package`.
