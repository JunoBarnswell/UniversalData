# Native remote bulk loading

SQL Destination uses the existing Connection Manager and Connector write entry. `loadMode` selects `auto`, `native` or `parameters`; the same options are available through `ud_write_options`. `UD_CONNECT_BATCH_WRITE` describes parameter batching, while `UD_CONNECT_NATIVE_BULK` describes an implemented native append transport. Explicit native loading requires the actual session capability and a proven operation before business effects. It never silently becomes parameter INSERT batching.

Data owns one bounded typed encoder and one SQL identifier/transport grammar. The encoder retains the sealed Batch and emits chunks without constructing a whole-batch string or temporary input file. Null markers, text delimiters, record separators, backslashes, control bytes, exact Decimal, UTC timestamps and binary values have provider-specific physical encoding under the same Data value semantics. Drivers transport bytes through their genuine client protocols rather than implementing another row evaluator or executor.

PostgreSQL uses authenticated libpq `COPY ... FROM STDIN` with cancellation and nonblocking backpressure. Binary columns use exact bytea hex; text containing NUL is rejected because PostgreSQL text cannot represent it. COPY and receipt reservation share the same database transaction; an unsuccessful transfer rolls back both. A successful transfer checks the server's row count before the ordinary commit/recovery path.

MySQL and MariaDB use their genuine client `LOAD DATA LOCAL INFILE` callbacks. The only accepted input is the current `ud-native-batch` token and its retained Native reader. No server-selected filename is opened. The session advertises native loading only when `local_infile` is available. Input uses binary character-set transport and explicit delimiter/escape bytes; BOOL and UTC timestamp representations follow their SQL domains. LOCAL INFILE warnings, missing input requests or row-count mismatch fail the operation instead of accepting skipped or coerced rows. Business writes and receipt insert share the proven InnoDB transaction.

The native transport supports append. Upsert uses the existing parameter path; an explicit native Upsert is rejected. SQL Server uses the vendor BCP SDK on a dedicated connection, loading a controlled global temporary table before business writes and receipts commit on the original connection. BCP receives the connected application HDBC, and UTC timestamps use the provider's canonical character representation. Generic ODBC advertises append and parameter arrays only when the connected driver proves transactional array support. Such a destination selects `delivery: response`: an uncertain commit enters recovery without automatic replay; it does not claim receipts, native bulk loading or distributed participation. SQL destinations default to `delivery: receipt`, requiring the connected driver's durable receipt capability. OCI Direct Path creates and loads controlled staging on its loader connection; the original connection applies business rows and receipts transactionally.

`ud_remote_bulk_benchmark` consumes the public C SDK and compares parameter/native transports against an isolated database using identical batches, one million rows, exact Unicode/control characters and receipt checks. Linux TCP/TLS measurements in this delivery show gains of 2.94× for PostgreSQL, 1.77× for MySQL, 1.37× for MariaDB and 1.98× for SQL Server BCP. They include driver write time and separate generation/CPU/RSS measurements; they describe the local acceptance resources, not a universal throughput guarantee. Oracle session attachment timed out, so OCI behavior and performance remain Blocked. The existing product model carries the evidence and remaining acceptance gaps.
